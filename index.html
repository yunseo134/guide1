0. 시험장에서 먼저 볼 것

작업 시작 전

항상 main 최신화 후 작업 브랜치를 만듭니다.

git checkout main
git pull origin main --no-rebase
git checkout -b docs/번호-작업내용

문제 생기면

바로 이것부터 확인합니다.

git status
git branch
git log --oneline --graph --all

충돌 났으면

marker를 지우고 최종 내용만 남깁니다.

# 파일 직접 수정 후
git add .
git commit -m "resolve conflict"
git push origin main

1. 역할별 해야 할 일

Branch Manager

브랜치 관리자

한 줄: main 직접 작업을 막고 브랜치 규칙을 확인하는 사람.

  • 현재 브랜치 확인: git branch
  • 작업 전 main 최신화 확인
  • 작업용 브랜치 생성 확인
  • 브랜치 이름에 issue 번호가 들어갔는지 확인

시험에서 할 말: “main에 직접 작업하지 않도록 확인하고, 작업 전 main을 최신화한 뒤 개인 branch에서 작업하도록 하겠습니다.”

git branch
git checkout main
git pull origin main --no-rebase
git checkout -b docs/3-readme-intro

Issue Manager

이슈 관리자

한 줄: 작업을 Issue로 나누고 담당자를 지정하는 사람.

  • GitHub → Issues → New issue
  • 작업 내용과 완료 기준 작성
  • Assignees에서 담당자 지정
  • PR에 Closes #번호 연결 확인

시험에서 할 말: “작업별 Issue를 만들고 담당자를 지정하겠습니다. Issue 번호를 branch와 PR에 연결하겠습니다.”

Issue 제목: docs/conflict-log.md 작성

## 작업 내용
충돌 발생 원인과 해결 과정을 기록합니다.

## 완료 기준
- 발생 파일 기록
- 충돌 원인 기록
- 사용 명령어 기록
- 최종 해결 방법 기록

PR Manager

PR 관리자

한 줄: PR이 제대로 작성됐는지 확인하는 사람.

  • base가 main인지 확인
  • compare가 작업 브랜치인지 확인
  • PR 제목과 설명 확인
  • Issue 연결 확인
  • 리뷰 없이 바로 merge하지 않도록 확인

시험에서 할 말: “PR 제목, 설명, Issue 연결, 대상 branch를 확인한 뒤 review를 받고 merge하도록 하겠습니다.”

제목: [#3] docs: add README intro

## 작업 내용
- README.md에 프로젝트 소개를 추가했습니다.

## 확인한 내용
- [ ] 개인 branch에서 작업했습니다.
- [ ] commit message를 의미 있게 작성했습니다.
- [ ] 관련 issue 번호를 연결했습니다.

Closes #3

Reviewer

리뷰어

한 줄: PR 변경 내용을 읽고 구체적인 comment를 남기는 사람.

  • PR → Files changed 확인
  • 문서 내용, 오타, 빠진 항목 확인
  • 브랜치 이름과 commit message 확인
  • “확인”만 쓰지 말고 구체적으로 comment
README 첫 문장이 프로젝트 목적을 잘 설명합니다.
다만 처음 보는 사람이 따라 하기 쉽도록 사용 방법을 한 줄 추가하면 더 좋겠습니다.

Recorder

기록자

한 줄: 오류, 충돌, 명령어, 해결 과정을 문서로 남기는 사람.

  • 누가 어떤 branch에서 작업했는지 기록
  • 오류 메시지 복사
  • 충돌 원인과 최종 결정 기록
  • 사용 명령어 기록
  • status/log 결과 요약

시험에서 할 말: “git status 결과와 오류 메시지를 먼저 기록하고, 충돌 원인과 해결 명령어를 conflict-log에 남기겠습니다.”

팀장 / Repository Owner

전체 조정

한 줄: 저장소와 전체 진행 상황을 관리하는 사람.

  • 저장소 생성, collaborator 초대
  • 기본 파일 생성
  • 역할별 진행 상황 확인
  • 막힌 팀원 조정

시험에서 할 말: “각자 branch에서 작업하고 PR과 review를 거쳐 main에 merge하도록 전체 흐름을 조정하겠습니다.”

2. 기본 Git 작업 흐름

개인 branch 작업 → push까지

git checkout main
git pull origin main --no-rebase
git checkout -b docs/번호-작업내용

# 파일 수정

git status
git add .
git commit -m "docs: 작업 내용 설명"
git push origin docs/번호-작업내용

PR merge 후 로컬 main 최신화

git checkout main
git pull origin main --no-rebase

3. Issue와 Pull Request

Issue는 어떻게 나누나?

작업 담당자가 따로 필요하면 Issue로 나눕니다. PR 하나로 해결할 만한 작업이면 Issue 하나가 적당합니다.

Issue브랜치PR 제목
#1 README 소개 추가docs/1-readme-intro[#1] docs: add README intro
#5 명령어 노트 작성docs/5-command-note[#5] docs: add command note
#6 충돌 기록 작성docs/6-conflict-log[#6] docs: add conflict log

PR 만드는 법

  1. 작업 브랜치 push
  2. GitHub 저장소 → Compare & pull request
  3. base: main, compare: 내 브랜치 확인
  4. 제목, 작업 내용, Closes #번호 작성
  5. Create pull request
  6. review 후 Merge pull request

4. 충돌 상황 대응

push rejected

원인: GitHub 원격 저장소가 내 로컬보다 최신입니다. 즉, 누군가 먼저 push했습니다.

git pull origin main --no-rebase
# 충돌이 없으면
git push origin 현재브랜치

일반 merge conflict

파일 안에 아래 표시가 생기면 최종 내용만 남기고 marker를 모두 지웁니다.

<<<<<<< HEAD
현재 branch 또는 main 쪽 내용
=======
병합하려는 branch 쪽 내용
>>>>>>> feature-branch
# 파일 직접 수정 후
git add .
git commit -m "resolve merge conflict"
git push origin main

modify/delete conflict

한쪽은 파일을 삭제하고, 다른 쪽은 같은 파일을 수정한 상황입니다. 파일을 살릴지 삭제할지 사람이 결정합니다.

파일 유지

# 파일 내용을 원하는 최종본으로 정리 후
git add note.txt
git commit -m "resolve modify/delete conflict by keeping file"
git push origin main

파일 삭제

git rm note.txt
git commit -m "resolve modify/delete conflict by deleting file"
git push origin main

merge를 취소하고 싶을 때

git merge --abort

5. status / log 해석

git status

현재 브랜치, 수정된 파일, staged 상태, 충돌 상태를 확인합니다. 문제가 생기면 가장 먼저 실행합니다.

git status

clean: 커밋할 변경 없음

MERGING: 병합 중, 충돌 해결 필요 가능

unmerged paths: 충돌 파일 있음

git log --oneline --graph --all

브랜치가 갈라지고 다시 merge된 흐름을 그래프로 봅니다.

git log --oneline --graph --all

HEAD → main: 현재 내가 있는 main 위치

origin/main: GitHub main 위치

|\, |/, *: 브랜치 분기와 병합 흐름

6. 기록 양식

docs/conflict-log.md

## 충돌 1

### 발생 파일
branch-conflict.txt

### 충돌 원인
두 branch가 같은 파일의 같은 줄을 서로 다르게 수정했다.

### 충돌 내용
- A 내용: 브랜치는 협업을 더 안전하게 만든다
- B 내용: 브랜치에서도 충돌은 발생할 수 있다

### 최종 결정
브랜치는 협업을 더 안전하게 만들지만 충돌은 여전히 발생할 수 있다.

### 사용한 명령어
git status
git add branch-conflict.txt
git commit -m "resolve branch merge conflict"
git push origin main

### 배운 점
충돌은 Git이 자동으로 정답을 고르지 못하는 상황이며, 사람이 최종 내용을 결정해야 한다.

docs/error-log.md

## 오류 1

### 상황
push를 실행했지만 rejected 메시지가 나왔다.

### 오류 메시지
Updates were rejected because the remote contains work that you do not have locally.

### 원인
원격 저장소가 내 로컬 저장소보다 최신이었다.

### 해결
git pull origin main --no-rebase로 원격 변경을 받은 뒤 다시 push했다.

### 사용한 명령어
git pull origin main --no-rebase
git push origin 브랜치명
